# NORA — Secrets & Environment Variables Cartography

> **Historical, as of the section below.** Written for the Azure deployment (Key Vault + Bicep +
> Container Apps), which is gone — no subscription, no export (ADR 0036). On the self-hosted stack,
> production secrets live encrypted in `infra/host/secrets.env.sops` (SOPS + age), decrypted to
> tmpfs on deploy; there is no Key Vault and no `secretRef`. See `docs/operations/host-deploy.md`
> §3 (Generate the age key and encrypt the secrets) for the current model and the current secrets
> inventory. GitHub Secrets/Variables below are still accurate for what CI itself needs — only the
> **production runtime** storage changed.
>
> **Operational document.** Last sweep: 2026-06-03 (senior audit).
> Repo: `https://github.com/sf0rzin/nora.git` · Default branch: `main` · GitHub environment: `dev` (no protection rules, **empty** — all secrets are at repository level).
>
> **Objective:** understand what each secret does, how to obtain/regenerate each one, and where it lives (GitHub Secret vs GitHub Variable vs `.env.local`). Includes a from-scratch recreation checklist.
>
> **Golden rule:** never commit real values. The `.env.example` files carry only variable **names**. In production (as originally written, on Azure), runtime secrets lived in the **Azure Key Vault** (generated/injected by Bicep), and the Container Apps consumed them via `secretRef` + Managed Identity (UAI) — the key never entered the browser bundle. On the self-hosted stack, the equivalent is SOPS + age (see the banner above).

## 1. Overview — the three configuration layers

NORA has **three** distinct planes where variables live. Do not confuse them:

| Layer | Where it lives | Who consumes it | Examples |
|---|---|---|---|
| **GitHub Secrets** (repo) | Settings → Secrets and variables → Actions → Secrets | The GitHub Actions workflows (`deploy-infra.yml` etc.) — they pass them to Bicep via `readEnvironmentVariable(...)` | `JWT_SECRET`, `OPENAI_API_KEY`, `PG_ADMIN_PASSWORD`, `CLOUDFLARE_TUNNEL_TOKEN` |
| **GitHub Variables** (repo) | same screen → Variables tab | Workflows, **non-secret** values | `NORA_EMAIL_FROM`, **`CF_ACCESS_AUD`** (today registered incorrectly — see §5) |
| **Azure Key Vault** | `nora-kv-dev-XXXXXX` (created by Bicep) | The Container Apps at runtime, via `secretRef` + UAI | `azure-speech-key` (generated by Bicep, does **not** come from GitHub), `postgres-password`, `jwt-secret`, `openai-api-key` (mirrors the GitHub Secret) |
| **`.env.local`** (dev) | the developer's machine (gitignored) | `docker compose`, Spring (spring-dotenv), Next dev, worker dev | `POSTGRES_PASSWORD=nora_dev`, `JWT_SECRET=change-me...`, optional `LLM_API_KEY` |

**Production flow (summarised):** GitHub Secret → (workflow `deploy-infra.yml` exports it as an env var) → Bicep `readEnvironmentVariable` → writes to the Key Vault → the Container App reads it via `secretRef`/UAI. Exception: `AZURE_SPEECH_KEY` is **generated by Bicep itself** (module `speech.bicep` → `key1`) and has no origin in GitHub.

## 4. How to obtain / regenerate each secret (step by step)

### LLM providers

**`OPENAI_API_KEY`** — main chat + NLP worker (default `gpt-4o-mini`).
1. Account: https://platform.openai.com/signup
2. Billing (requires a card): https://platform.openai.com/account/billing
3. Generate the key: https://platform.openai.com/api-keys → "Create new secret key" → copy (format `sk-...`, shown only once).

**`DEEPSEEK_API_KEY`** — multi-provider chat (ADR 0024, live model switching).
1. Account: https://platform.deepseek.com/
2. API keys: https://platform.deepseek.com/api_keys → create a key.

**`GEMINI_API_KEY`** — chat/multimodal (Google AI).
1. Google AI Studio: https://aistudio.google.com/app/apikey → "Create API key" (associated with a Google Cloud project).

> All three are **optional**: empty → the corresponding provider becomes unavailable, but the system does not break (empty OpenAI = worker in stub and chat 503).

### Email

**`RESEND_API_KEY`** — transactional email sending (account verification, password reset).
1. Free account (3,000 emails/month): https://resend.com/signup
2. API key: https://resend.com/api-keys → "Create API Key" (format `re_...`).
3. **Important:** to use `NORA_EMAIL_FROM = NORA <noreply@nora.systems>`, the domain `nora.systems` must be **verified** at https://resend.com/domains (add DNS records — SPF/DKIM). Until it is verified, use `onboarding@resend.dev` (sandbox).
4. Empty → the backend falls back to `LogEmailSender` (links appear in the app log, no real email).

### Azure (federated OIDC — no client secret)

**`AZURE_CLIENT_ID`**, **`AZURE_TENANT_ID`**, **`AZURE_SUBSCRIPTION_ID`** — GitHub Actions authentication to Azure via OIDC.
1. App Registration `sp-nora-github-deploy` in Entra (tenant `fiap.com.br`):
   `az ad app create --display-name sp-nora-github-deploy` → note the `appId` (= `AZURE_CLIENT_ID`).
2. `AZURE_TENANT_ID`: `az account show --query tenantId -o tsv`.
3. `AZURE_SUBSCRIPTION_ID`: `az account show --query id -o tsv`.
4. Service Principal + Contributor role **scoped to the RG** (not the subscription):
   `az role assignment create --assignee <appId> --role Contributor --scope /subscriptions/<sub>/resourceGroups/rg-nora-dev`
5. **Federated credentials** (3 subjects — no password):
   - `repo:sf0rzin/nora:ref:refs/heads/main`
   - `repo:sf0rzin/nora:pull_request`
   - `repo:sf0rzin/nora:environment:dev` (required because the `deploy` job uses `environment: dev`)
   Via the portal: App Registration → Certificates & secrets → Federated credentials → Add. Issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`.
   Docs: https://learn.microsoft.com/azure/developer/github/connect-from-azure-openid-connect

### Postgres (random passwords)

**`PG_ADMIN_PASSWORD`** (main Postgres) and **`PG_PLATFORM_ADMIN_PASSWORD`** (2nd Postgres of the control plane).
- Bicep requires `@minLength(12)`. Generate distinct strong passwords:
  - PowerShell: `[Convert]::ToBase64String((1..32 | %{ Get-Random -Max 256 }))`
  - bash: `openssl rand -base64 32`
- Paste each one into the corresponding Secret. **Do not reuse** between the two Postgres instances (isolated blast radius, ADR 0022).

### Auth / internal tokens

**`JWT_SECRET`** — HMAC secret of the JWTs (HS256, min 32 chars).
- `openssl rand -base64 48`  (or `https://generate-secret.vercel.app/32`)
- `application-prod.yml` rejects the public placeholder outside local/test (fail-closed).

**`NORA_PLATFORM_INTERNAL_TOKEN`** (service→service) and **`NORA_PLATFORM_ADMIN_TOKEN`** (console→API) — opaque control plane tokens.
- Generate two **distinct** values (least-privilege):
  `openssl rand -hex 32`  (run it twice)
- If they are left empty with `enablePlatform=true`, they become `'unset'` in the KV and unlock admin/internal — **always set them** before go-live.

### Cloudflare (control plane v2 — ADR 0025)

**`CLOUDFLARE_API_TOKEN`** — used by the `cloudflare-setup.yml` and `cloudflare-tunnel.yml` workflows.
1. https://dash.cloudflare.com/profile/api-tokens → "Create Token" → Custom token.
2. Minimum permissions (critical path):
   - Account · Access (Apps and Policies) · **Edit**
   - Account · Access (Service Tokens) · **Edit**
   - Account · Cloudflare Tunnel · **Edit**
   - Zone · DNS · **Edit**
   - Zone · Zone · **Read**
3. Optional (full automation, creates the OTP IdP via API): Account · Access (Organizations, Identity Providers, and Groups) · **Edit**.
4. Scope it to the `nora.systems` zone.

**`CLOUDFLARE_TUNNEL_TOKEN`** — connector token of the nora-admin tunnel.
1. Run the `cloudflare-tunnel.yml` workflow (workflow_dispatch) to create/reuse the tunnel.
2. The token **does not appear in the log**: this repo is public (ADR 0017) and a run's log is readable by
   any visitor. The step `AUD + connector token instructions` prints the command to fetch it
   straight from the API and pipe it into the secret, without the value touching a log or the shell history:
   ```bash
   export CF_TOKEN=<the same CLOUDFLARE_API_TOKEN>
   curl -fsSL -H "Authorization: Bearer $CF_TOKEN" \
     "https://api.cloudflare.com/client/v4/accounts/<account-id>/cfd_tunnel/<tunnel-id>/token" \
     | jq -r .result | gh secret set CLOUDFLARE_TUNNEL_TOKEN --repo sf0rzin/nora
   ```
3. Rotation: recreating the tunnel through the same workflow generates a new token.

**`CF_ACCESS_AUD`** — AUD tag of the Access App `admin.nora.systems` (a **public**, non-secret identifier).
1. It appears in the log of the `AUD + connector token instructions` step of `cloudflare-tunnel.yml` (`cloudflare-setup.yml`, which creates the Access App, must have run before).
2. Register it as a **Variable** `CF_ACCESS_AUD` (see §5 — today it is a Secret, which is wrong).

### Registry (optional)

**`REGISTRY_PASSWORD`** — only if the GHCR images are private. A GitHub PAT with the `read:packages` scope (https://github.com/settings/tokens). Today the images are public → not needed.

## 5. Inconsistencies found (fix before/after recreating)

### 5.1 CRITICAL — `CF_ACCESS_AUD` registered as a Secret but read as a Variable
- **Symptom:** `deploy-infra.yml` lines 124 and 176 use `CF_ACCESS_AUD: ${{ vars.CF_ACCESS_AUD }}`. There is no Variable with that name (only `NORA_EMAIL_FROM`). The value arrives **empty** in Bicep (`cfAccessAud=''`), so nora-admin **does not validate the audience** of the Cloudflare Access JWT → Tier 2 degrades to edge-only, **silently**.
- **Evidence:** `cloudflare-tunnel.yml` itself (lines 163, 185) instructs setting it as a **Variable**, and the comment in `deploy-infra.yml` (line 25) says "not-secret". So the Secret was registered in the wrong place.
- **Fix (choose one):**
  - **(A) recommended:** delete the `CF_ACCESS_AUD` Secret and create a **Variable** `CF_ACCESS_AUD` with the same value (the AUD is public). No code change.
  - (B) change the workflow to `${{ secrets.CF_ACCESS_AUD }}` (keeping it as a Secret) — it works, but it contradicts the design (the AUD is not a secret) and the runbook.

### 5.2 MEDIUM — `EASYAUTH_CLIENT_ID` / `EASYAUTH_CLIENT_SECRET` orphaned in the workflow
- Referenced in `deploy-infra.yml` but they do not exist as Secrets. Inert per ADR 0025 (Entra abandoned in favour of Cloudflare). They resolve empty without breaking. **I recommend removing the 4 lines** from the workflow to reduce confusion.

### 5.3 LOW — Control plane health telemetry not provisioned
- `NORA_PLATFORM_HEALTH_APP_ID` / `NORA_PLATFORM_HEALTH_API_KEY` are neither in a Secret nor in Bicep. The operator's health panel (App Insights REST) stays "unavailable". If you want to turn it on: create an App Insights API key (`nora-ai-dev`) and the App ID, and provision them as env vars of the API's Container App (today this requires editing the Bicep — there is no param).

### 5.4 LOW — `NORA_EMAIL_FROM` points to a non-sandbox domain
- Variable = `NORA <noreply@nora.systems>`. It only works if `nora.systems` is **verified in Resend**. Otherwise, emails fail silently. Check at https://resend.com/domains or go back to the sandbox `onboarding@resend.dev`.

### 5.5 INFORMATIONAL — Dependabot/supply-chain
- Dependabot's "npm_and_yarn in /apps/web" run is **failing** and **Dependabot alerts are disabled** in the repo. It is not a secret, but it is security debt that matters for a production SaaS. Enable it in Settings → Code security.
