# ADR 0036 — The substrate is a single bare-metal Ubuntu host, not a Proxmox VM

- **Status:** accepted
- **Date:** 2026-08-10
- **Supersedes:** ADR 0034 §1 (substrate) and §9 (backup). Everything else ADR 0034 decided —
  Cloudflare Tunnel as the only ingress, SOPS + age, pull-based deployment, the two Postgres
  servers, the observability pair, the excluded scope — is unchanged and still in force.
- **Related:** ADR 0017 (public repo, which is what vetoes push deployment), ADR 0025 (tunnel),
  ADR 0026/0028 (RLS), `infra/host/docker-compose.yml` (the stack contract),
  `docs/operations/host-deploy.md` (runbook)

## Context

ADR 0034 decided to migrate to "a single Debian VM on Proxmox". That decision was recorded on
2026-08-07, before the machine existed. What was then provisioned is not that.

Verified by inspection of the running host on 2026-08-10:

| ADR 0034 said | What runs |
|---|---|
| Debian | Ubuntu 24.04.4 LTS, kernel 6.8 |
| A VM on a Proxmox hypervisor | Bare metal. `systemd-detect-virt` returns `none` |
| "an idle home Proxmox (`beta`)" | A single dedicated host. There is no hypervisor and no other guest |
| VM snapshots on a Proxmox Backup Server | No Proxmox Backup Server exists. That leg of the backup design was never built |

Everything else in ADR 0034 was built as written: compose project `nora` with fourteen
containers, the three bridge networks, no port published on the host, `cloudflared` dialling
out to Cloudflare with Caddy behind it, secrets in `secrets.env.sops` decrypted on the host
into tmpfs, and the pull agent (`nora-deploy.timer` → `deploy.sh --if-changed`).

The gap is therefore narrow and entirely in the substrate description — but it is load-bearing,
because a directory named `infra/proxmox/`, a runbook named `proxmox-deploy.md` and a workflow
named `deploy-proxmox.yml` all assert a hypervisor that a reader will look for and not find.

### Azure is gone, not being decommissioned

ADR 0034 planned an orderly `az group delete` as step 5. That step will not be executed, because
there is nothing left to delete: the subscription is gone, there is no export and there is no
data to restore. `docs/operations/azure-decommission.md` described a shutdown order for
resources that no longer exist, and `infra/bicep/` described how to create them.

### Recovery is rebuild-from-repo

There is no second machine, no hypervisor snapshot and no off-host copy of anything except what
is in this repository. That is a deliberate proportion, not an oversight: ADR 0034 §"There is no
data to preserve" established that the database holds reproducible demonstration content, and
nothing since has changed that.

What it does change is where the risk sits. With restore-from-copy unavailable, the recovery
procedure is *rebuild from this repository*, and that procedure is only as good as the
repository's fidelity to the host. A change made by hand on the host and not committed is not a
tidiness problem; it is an unrecoverable one, because nothing else records it.

## Decision

**Record the substrate as a single bare-metal Ubuntu host running Docker Compose, and rename
every path that asserts otherwise.**

### 1. Substrate

One physical host, Ubuntu 24.04 LTS, Docker Engine with Compose v2, compose project `nora`. No
hypervisor, no VM, no orchestrator. The three-network topology (`edge`, `internal`, `data`, the
last two `internal: true`) and the "no published port other than loopback" rule from ADR 0034 §1
are unchanged and were verified in place.

Consequence worth stating rather than implying: ADR 0034's "single host = single point of
failure" paragraph gets slightly worse. On a VM, a host that survives can restart the guest;
here the host is the guest. The verdict is the same — an educational project accepts the
downtime — but the mitigation ADR 0034 named (rehearse the boot beforehand) is now the only one.

### 2. Naming

| Was | Is |
|---|---|
| `infra/proxmox/` | `infra/host/` |
| `docs/operations/proxmox-deploy.md` | `docs/operations/host-deploy.md` |
| `.github/workflows/deploy-proxmox.yml` | `.github/workflows/deploy-host.yml` |

The systemd unit and timer are generated by `infra/host/scripts/bootstrap-host.sh`, so the path
change reaches the host by re-running that script's unit section — there is no hand-edited unit
file to drift.

### 3. Backup

ADR 0034 §9 specified two legs: an hourly logical `pg_dump` with 14-day retention, and a VM
snapshot on a Proxmox Backup Server. The first leg exists and runs — the `backup` service writes
to `/srv/nora/backups` on the hour, with a `.sha256` and a `.toc` beside each dump. The second
leg has no substrate to run on and is withdrawn rather than left on paper.

So the honest statement of the recovery position is: **the database has an hourly on-host dump
and nothing off-host; the code, the configuration and the infrastructure definition have GitHub.**
An on-host dump survives a bad migration, a wrong `DELETE`, or a `docker compose down -v`. It
does not survive the loss of the host. Given that the content is reproducible demonstration
material, that asymmetry is accepted deliberately — but it is the reason `infra/host/` must keep
reproducing the machine, because for everything that is *not* the database, the repository is the
only copy.

### 4. The encrypted secrets file stays off the repository

ADR 0034 §4 says `secrets.env.sops` is "versioned encrypted", and `.gitignore` still carries a
`!` rule to force-include it. In practice it has never been committed on any ref: it exists only
on the host, untracked. This ADR makes that the decision rather than the accident.

The reason is that versioning it buys nothing here. ADR 0034 §4 also puts the age *private* key
only on the host, and its own bootstrap output says that without an offline copy of that key the
encrypted file "turns into garbage". There is no offline copy. So in the one scenario where a
versioned ciphertext would help — the host is gone — the key needed to read it is gone with it.
What the repository would gain is nothing; what it would carry is the permanent, public,
non-retractable ciphertext of every live production secret. A public repository never forgets, and
`git revert` does not unpublish.

So the honest recovery statement, which belongs next to the rebuild-from-repo model above: **the
secrets are the one part of the host this repository does not reproduce.** A rebuild regenerates
them from `secrets.env.example`, which lists every key with its shape. For a project whose
credentials are a handful of generated passwords and re-issuable third-party API keys, regenerating
is cheaper than the disclosure risk of the alternative — and it is what would actually happen.

The `!infra/host/secrets.env.sops` rule in `.gitignore` stays. It costs nothing, it documents the
intent, and if an offline age-key backup ever exists the decision can be revisited by committing
the file, with no other change.

### 5. Azure

`infra/bicep/` and `docs/operations/azure-decommission.md` are deleted. `docs/operations/azure-deploy.md`,
already marked historical by ADR 0034, is deleted with them.

They document the creation and the orderly shutdown of a subscription that no longer exists.
Keeping them as "history" would mean keeping three documents whose every instruction is
inapplicable, in a repository whose stated standard is that documentation describes what is
true. Git holds the history; `git log -- infra/bicep` is where it belongs.

Azure keeps exactly one place in this repository from now on: the past tense, inside ADRs, where
it is a decision that was made and then reversed.

## Consequences

- ADR 0034 remains the decision to leave Azure and the record of *why* every component is shaped
  the way it is. It is not edited. This ADR corrects two of its facts and inherits the rest.
- Because it is not edited, ADR 0034's "Application Plan" section keeps two links that now point at
  nothing: the renamed runbook and the deleted decommission runbook. They are declared in
  `scripts/check-doc-links.sh` as an exact `file|target` pair each, so the check still fails on any
  *other* broken link in that same ADR. The alternative — repairing the pointers — would mean
  editing an accepted decision to keep a script quiet, which is the wrong way round.
- `scripts/check-language.sh` loses its section-8 allowlist entry, which existed only for
  `infra/bicep/` and named the directory's deletion as the thing that would close it.
- The 8 "Azure for Students pitfalls" catalogued in `azure-deploy.md` are lost with that file.
  They were specific to a platform this project no longer touches; the self-hosting pitfalls that
  replaced them live in `docs/operations/host-deploy.md`.
- Anyone reading `git log` before 2026-08-10 will find `infra/proxmox/` at the old path. The
  rename is a `git mv`, so `--follow` traverses it.

## Alternatives Considered

1. **Edit ADR 0034 to say "bare-metal Ubuntu host".** Rejected. Accepted ADRs are immutable —
   ADR 0034 is the record of a decision taken on 2026-08-07 with the information available then,
   and rewriting it would erase the fact that the plan and the build diverged. That divergence is
   the useful part.
2. **Leave the paths alone and note the discrepancy in the runbook.** Rejected. A directory name
   is read far more often than the paragraph explaining it, and `infra/proxmox/` makes a reader
   look for a hypervisor. The rename is mechanical and `git mv` preserves history.
3. **Keep `infra/bicep/` and the Azure runbooks as history.** Rejected, and this is the one worth
   arguing. The argument for keeping them is that they record how the thing used to be built. But
   they are not a record — they are instructions, written in the imperative, for a subscription
   that cannot be created because nobody is paying for it. A reader who follows them gets nothing.
   Git already keeps them, addressable and diffable, which is what "keeping history" actually
   means.
4. **Build a real off-host backup (object storage, a second machine).** Rejected for the same
   reason ADR 0034 rejected pgBackRest: it is proportionate to production data, and there is
   none. Recorded here as the change to make if that ever stops being true, together with its
   trigger — the first tenant whose content is not reproducible.
